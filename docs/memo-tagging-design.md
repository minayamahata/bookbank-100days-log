## 0. 目的と背景

### 0.1 何を解決するか

N0スパイク（`docs/n0-spike-results.md`）で確認したとおり、メモ本文からの**自動**キーワード抽出には構造的な限界がある:

- 日本語・韓国語は `NLTagger` の品詞タグ非対応で、助詞・形式名詞の混入をストップワード辞書とIDFで事後抑制するしかない
- 「私的な語」（例: 旅行の行き先、貸した相手の名前）が偶然一致すると、ユーザーの意図しない弱いエッジができる
- 逆に、ユーザーが「この2冊はつながっている」と思っていても、共通語がなければエッジはできない

**タグは、この自動抽出の裏返しとして「ユーザーが意図して本をつなげる」明示的な手段**を提供する。`#京都` と2冊のメモに書けば、その2冊は確実に・強く・理由つきでつながる。自動抽出が「機械の推測（弱い・玉石混交）」、タグが「人間の宣言（強い・確実）」という役割分担になる。

### 0.2 スコープの判断（Markdownではなくタグに絞る）

オーナーの要望は「タグや**Markdown的な要素**」だったが、初期スコープは **`#タグ` 記法のみ** とする（**確定・2026-08-07**）。理由:

- 見出し・太字などの装飾記法は「本をつなげる」という目的に寄与せず、レンダラー実装（5言語・ダークモード・エクスポート互換）のコストだけが増える
- 既存のMarkdownエクスポート機能（`Utils/MarkdownExporter.swift`）との記法衝突を避ける検討が別途必要になる
- タグ単体なら正規表現1本で完結し、R4.5の小リリース規模に収まる

装飾記法が将来必要になれば、タグと独立に追加できる（本書の設計はそれを妨げない）。

## 3. 記法設計（T1）

### 3.1 記法の選定

| 案 | 内容 | 判定 |
|----|------|------|
| **A: `#タグ`** | Twitter/Instagram等で広く浸透。入力が軽い（1文字＋語）。5言語すべてで同じ記法 | **採用（確定・2026-08-07）** |
| B: `[[タイトル]]` | Obsidian式の直接リンク。本のタイトルを正確に入力する負担が大きく、表記ゆれで壊れる | 初期スコープ外（将来、タグで不足したら再検討） |
| C: `@メンション` | 「人」の含意が強く、本をつなげる用途に不自然 | 却下 |

「誰でも簡単に」という要望に対し、`#` は説明不要の記法として最有力。SNS経験のあるユーザーは教わらなくても使える。

### 3.2 パース仕様

```
直前境界 = 行頭（文字列先頭）・空白・改行 のいずれか、または 直前のタグが終わった位置
           ← これ以外の位置の # はタグ開始と見なさない
開始記号 = "#"(U+0023) または "＃"(U+FF03)
タグ本体 = Unicode一般カテゴリ L* / M* / N* / "_" の連続（1〜30文字）
終端     = 上記に該当しない文字（空白・改行・句読点・記号・絵文字）・文字列末尾
無効     = 十進数字のみ（#1, #2026）・空（# 単体）・31文字以上（切り捨てず不成立）
```

- **正規表現ベース**で実装する。`NLTagger` 等のNLPは使わない → 日本語・韓国語の品詞タグ非対応問題（N0結果メモ・ノード設計書 3.1節）の影響を**受けない**。5言語で同一の挙動
- 抽出後の正規化はノードと同じ **NFKC＋小文字化**（`＃京都`＝`#京都`、`#SF`＝`#sf` を同一タグとする）
- **本棚内検索の正規化とは意図的に別物である（2026-08-07 オーナー確定）**: 既存の `Utils/ShelfSearchMatcher.normalize` は `applyingTransform(.hiraganaToKatakana)` ＋ `folding(.caseInsensitive/.widthInsensitive/.diacriticInsensitive)` ＋ 空白除去で、**ひらがなをカタカナへ寄せる**。NFKC はこれを行わないため、`#とうきょう` と `#トウキョウ` は**別タグ**になる（本棚内検索では同一視される）。同じアプリ内に2つの正規化が併存することになるが、これは**役割の違いによる意図的な差**である——**検索は表記ゆれを吸収するのが目的、タグはユーザーが書き分けたものを区別するのが目的**。加えて、タグはT2で `bookIndex.keywords` に載りノード側の自動抽出語と突き合わされるため（5.1節）、**ノードの正規化と揃っている必要がある**。実用上の表記ゆれは 4.1節の入力サジェスト（既存タグを候補に出す）で発生自体を抑える
- **開始記号は半角 `#` と全角 `＃` の両方を受ける（確定・2026-08-07）**。3.2節が「`＃京都`＝`#京都`」と書いていたのは**正規化後**の同一視の話であり、パーサが `＃` を開始記号として認識するかは別問題だった。**日本語IMEのかな入力で `#` を打つと全角 `＃` が出るため、ここを受けないと日本語ユーザーの大半がタグを打てない**（機能の成立条件）
- **`#` の直前に「行頭・空白・改行」のいずれかを要求する（確定・2026-08-07）**。この条件が無いと、メモに貼ったURLの `https://example.com/#section` が `#section` というタグになり、`C#の本` が `#の本` になる。**誤検出と取りこぼしでは壊れ方が違う**——誤検出は既存の本棚のメモに黙ってゴミタグを生やすが、取りこぼしはユーザーが空白を1つ入れれば直せる。**静かに壊れるほうを潰す**という判断でこの厳しめの条件を採る
  - 緩める案（Twitter方式＝直前が文字・数字でなければタグ）も検討したが、URLの `/#section` を拾うため採らない
  - **連続タグ（`#京都#奈良`）は例外として許す（緩和・2026-08-07 オーナー確定）**: 上の条件だけだと2つ目の `#` は直前が文字なので開始記号にならず、`#京都` しか取れない。しかし**日本語圏のSNSでは連続ハッシュタグが標準的な書き方**であり、取りこぼしの規模のわりに緩和の範囲が狭いため割に合う。実データを待たずに入れた理由は、**既存メモはタグ機能が無かった時代のものなので「連続タグをどう書くか」を測れない**から（N0エクスポートで分かるのは誤検出の有無だけ）
    - **緩和の正確な形**: オーナー指示は「`#` の直後も許す」だったが、`#京都#奈良` の2つ目の `#` の直前文字は `都` であり `#` ではないため、その条件では目的の結果にならない。実装した規則は「**タグとして成立した直後の位置も境界と見なす**」。オーナーが挙げた安全性の根拠（`/#section` は直前が `/`、`C#の本` は直前が `C`）はこの形でもそのまま成立する——どちらも「直前にタグが成立していない」ため従来どおり弾かれる
    - **成立しなかったタグの直後では境界は復活しない**。したがって `##京都` は従来どおり何も取れない（1つ目は本体が空で不成立）
  - **後から緩めるのは容易だが、狭めるのは既に使われているタグを壊すので困難**。7章のN0エクスポートでの実データ確認で取りこぼしが目立つようなら、「、#京都」「「#京都」のような**句読点・括弧の直後を許す**方向への緩和を再検討する（連続タグとは違い、こちらは既存メモから実態を測れるため実データ確認後の判断とする）
- **「数字のみ無効」は十進数字（Unicode `Nd`）に限る（2026-08-10 実装時に明確化）**: `Character.isNumber` は `京`・`十`・`一` のように**数値を持つ漢字**も数字と判定するため、その定義で実装すると `#京` のような正当なタグまで弾かれる（実装中にテストで検出した）。判定は「全文字が `Nd`」に限定する。`#2026` と `#１`（NFKCで半角化）は従来どおり無効、`#京` は有効
- パーサは**純関数**（`String → [Tag]`、Tagは表示位置レンジ＋正規化キー）としてユニットテスト対象にする（実装ガイド 5章）
- 既存メモに偶然含まれる `#` の誤検出は、上の直前境界＋「数字のみ無効」＋文字種による終端で抑制する（例: `#1位` は「1位」が数字始まりでも文字を含むため有効になる — **許容で確定・2026-08-07**。直前境界の条件があるため誤検出の心配はない）

### 3.3 なぜスキーマ変更ゼロで成立するか

タグは「メモの中に既にある文字列」であり、データとして二重管理しない:

- **表示時**: メモ文字列をパースしてハイライト（`AttributedString`）
- **集計時**（サジェスト・絞り込み）: 全書籍のメモをパースしてタグ→本のインデックスをメモリ上に構築（425冊規模なら数ms・キャッシュはメモリのみ）
- **T2**: ノードのインデックス生成パイプラインが元々メモ本文を読んでいる（ノード設計書 3章）ので、その中でタグも抽出する — 保存先は既存計画の `bookIndex.keywords` であり、SwiftData/Firestoreのユーザーデータスキーマには触れない

### 4.2 T1でやらないこと

- タグの編集・リネーム・削除の専用UI（メモ本文を編集すれば変わる。それがスキーマレスの利点）
- タグ一覧画面・タグクラウド（絞り込み導線で十分。利用状況を見て判断）
- Markdown装飾（0.2節）・`[[直接リンク]]`（3.1節）
- ノードグラフとの連携（T2 = R5）
- **月メモ（`MonthlyMemo.text`）のタグ**（4.3節）

### 4.3 月メモをT1のスコープから外す理由（2026-08-07 オーナー確定）

初版ドラフトは対象を `UserBook.memo` と `MonthlyMemo.text` の双方 (仮) としていたが、実装調査の結果 **T1では書籍メモのみを対象とし、月メモは T2以降の検討項目へ送る**ことに決めた（8章）。理由は2つ。

1. **ハイライトの表示箇所が存在しない**: 月メモの本文は、編集中の `MemoEditorView` の `TextEditor` の中以外、**カレンダーを含めどの画面にも表示されていない**（`BookshelfCalendarView` にあるのは編集ボタンのみ）。したがってタグをパースしてもハイライトを出す場所が無く、T1の機能のうち「表示」が成立しない
2. **インデックスの形が変わる**: 書籍メモのタグは「タグ → 本」で直接結びつくが、月メモのタグは「タグ → 月 → その月に読んだ本すべて」という間接的な結びつきになる。これは 3.3節のインデックス（タグ→本）とは別の構造を要し、絞り込みの意味論（その月の本を**すべて**そのタグとみなしてよいのか）も別途決める必要がある

月メモのタグを扱うなら、この意味論を決めたうえで T2 のエッジ設計（「メモ同月」軸が既に 5.2節にある）と併せて考えるのが筋である。

### 4.4 タグのタップ導線は「詳細画面のタグチップ行」（2026-08-07 オーナー確定）

初版は「メモ内のタグを直接タップして絞り込む」（案a）を想定していたが、**書籍詳細にタグチップの行を足し、操作はそのチップが持つ**（案b）に決めた。メモ本文の着色は「これはタグである」という**表示**のまま残し、**操作はチップが持つ**という役割分担である。同じタグが本文とチップに二重に出るが、意味が違うので冗長にはならない。実装はT1のタグ絞り込み（4.1節）とまとめて行う。

**案bを採る理由**:

1. **タップ先が衝突しない**。`UserBookDetailView` のメモ欄は全体が「タップでメモエディタを開くボタン」であり（`UserBookDetailView.swift` の `showMemoEditor`）、メモの一部だけ挙動が変わると**誤タップしたとき何が起きたか分かりにくく、戻る操作も直感的でない**
2. **本棚の絞り込みUIでチップ方式を選んだ判断と揃う**（4.1節）。同じ「タグを操作する要素」が画面ごとに別の形をしているより、一貫しているほうが説明が要らない
3. **タグが1つも無い本では行ごと出ない**ので、タグを使わない人の詳細画面は現状のまま維持される。チップ方式を選んだときと同じ理屈

## 5. ノードグラフ連携（T2・R5ノードβに同梱）

### 5.1 統合点

ノード設計書のパイプライン（正規化→言語判定→抽出→ストップワード→IDF）に対し、タグは**別レーンで合流**する:

```
メモ本文 ─┬─ 自動抽出レーン: NLTagger/フォールバック → ストップワード → IDF → keywords (source: "memo")
          └─ タグレーン:     正規表現パース（3.2節）→ そのまま採用   → keywords (source: "tag")
```

- タグレーンには**ストップワードもIDF減衰も適用しない**。ユーザーが意図して書いた語を機械が却下しない（前提7）
- `bookIndex.keywords` の要素に `source: "tag" | "memo" | "title"` を持たせる（R5は最初からFirestore保存＝N2統合のため、ローカルキャッシュの移行は発生しない。schemaVersionの初版に含める）

### 5.2 エッジ重み（順序のみ確定・2026-07-19）

**確定しているのは順序関係のみ**: シリーズ 1.0 > **タグ共有** > 著者 0.6。**タグの具体値はノードβの実データで調整する**（オーナー確定・2026-07-19）。

| 軸 | 重み | 備考 |
|----|------|------|
| シリーズ | 1.0 | 既存（ノード設計書 5章） |
| **タグ共有** | **1.0と0.6の間（具体値はノードβで調整）** | **新設**。「ユーザーの宣言」はシリーズ判定に次ぐ確実さ。reasons表示は「#京都」 |
| 著者 | 0.6 | 既存 |
| 共有キーワード | 0.15×IDF（3個上限） | 既存・自動抽出 |
| メモ同月 | 0.05 | 既存 |

- タグ共有はエッジ上限（k=8）・スコア下限の枠組みには従う（タグだけ特別扱いして毛玉化したら本末転倒）
- 同一タグを大量の本に付けた場合（例: 30冊に `#積読`）は完全グラフ化して毛玉になるため、**1タグあたりのエッジ生成上限 (仮: 共有本数が15冊を超えるタグはエッジ生成から除外し、絞り込み機能でのみ有効)** を設ける — 自動抽出のIDF足切りと同じ思想の、タグ版の安全弁
- タグ重みの具体値の調整には N0ハーネスを再利用できる（タグ軸を足して再走）

### 5.3 自動抽出との関係

タグが普及すれば「メモ由来の自動抽出語」の役割は縮小しうるが、**当面は併存** (仮・前提8)。タグを1つも使わないユーザーにも自動のつながりは価値があるため。ノードβでの実測（タグ利用率・雑音エッジ報告）を見て、メモ自動抽出語の重み引き下げ・廃止を判断する。

## 7. リスクと対策

| リスク | 対策 |
|--------|------|

| 5言語での入力性 | `#` は全キーボードで入力可能。ハングル・中文のタグはパーサが文字クラスで対応（3.2節）。テストデータはN0の5言語テスト棚を流用 |
