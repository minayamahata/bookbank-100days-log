## 0. 目的と背景

### 0.1 何を解決するか

N0スパイク（`docs/n0-spike-results.md`）で確認したとおり、メモ本文からの**自動**キーワード抽出には構造的な限界がある:

- 日本語・韓国語は `NLTagger` の品詞タグ非対応で、助詞・形式名詞の混入をストップワード辞書とIDFで事後抑制するしかない
- 「私的な語」（例: 旅行の行き先、貸した相手の名前）が偶然一致すると、ユーザーの意図しない弱いエッジができる
- 逆に、ユーザーが「この2冊はつながっている」と思っていても、共通語がなければエッジはできない

**`[[ ]]` は、この自動抽出の裏返しとして「ユーザーが意図して本をつなげる」明示的な手段**を提供する。`[[京都]]` と2冊のメモに書けば、その2冊は確実に・強く・理由つきでつながる。自動抽出が「機械の推測（弱い・玉石混交）」、`[[ ]]` が「人間の宣言（強い・確実）」という役割分担になる。

### 0.2 用語の定義（2026-08-10 オーナー確定）

`[[ ]]` は「タグ」ではない。**BookBank のノードは本であり、`[[ ]]` の中身はエッジの理由**にあたる。

| 文脈 | 言葉 |
|------|------|
| UIの操作 | **つなぐ**（ツールバーのボタン名） |
| UIのできたもの | **つながり**（チップ・絞り込みの表示） |
| 開発側 | **エッジ／ラベル**。`[[中身]]` の中身＝エッジの理由（ラベル）。型名は `MemoLink*`（R5の実際のエッジ型と名前がぶつからない） |

### 0.3 方式転換の経緯（`#` 廃止・2026-08-10 オーナー確定）

初版〜2026-08-07 のT0クローズまでは `#タグ` 記法を採用し、パーサ・ハイライト・サジェストまで実装済みだった（9章）。転換の判断は次の連鎖による:

1. `#` の最大の実務問題は**入力**だった——日本語IMEのかな入力では全角 `＃` が出るため受け口を広げ、さらに記号そのものを打たせる負担が残っていた
2. その解決策として**メモ編集欄へのツールバー新設**（4.5節）が決まった。ボタンが記号を挿入するなら、記号が `#` である必要はない
3. 一時はタグを**本のデータ項目（タグ欄）**として持つ案も検討したが、ツールバーが入力問題を解くなら**別欄を設ける動機がなくなる**。スキーマ変更ゼロ（前提1）を保ったまま、メモ内記法の一本化で足りる
4. 記法を1つに絞るなら、「本と本をつなぐ線」という目的をそのまま表せる `[[ ]]` を選ぶ（3.1節）

**`#` 記法は未リリース**（R4.5の開発中のみ存在）のため、ユーザーデータに `#` タグは存在せず、移行・互換の問題はゼロ。

### 0.4 スコープの判断（Markdownは「ツールバーが出せるもの」だけ解釈する）

初版は「Markdown装飾はやらない・タグのみ」だったが、ツールバー新設に伴い**太字 `**` と行頭の引用 `>` に限って解釈（レンダリング）する**（2026-08-10 オーナー確定）。

- **挿入のみ（表示は素のまま）は採らない**: ボタンを押したのに詳細画面で `**` が生のまま見えるのでは、ユーザーから見て機能として成立しない
- **解釈するのはツールバーが出せるものだけ**: 見出し・箇条書き・斜体・リンクなど他のMarkdown記法は解釈しない。「**ボタンで入れたものだけが装飾になる**」という約束を保つためで、既存メモに偶然含まれる記号が意図しない装飾になるリスクもここで最小化する。`*` 1つの斜体を外すのも同じ理由
- **文字色・フォント変更は入れない**: ① つながりの着色（テーマ色）と衝突する ② 黒テーマ＋ダークモードで可読性が崩れる ③ Markdownに無いので独自記法が必要になる
- **ページ番号ボタンは文字（`p.`）を挿入するだけの入力補助**（4.5節）。ただし表示側は `p.数字` をバッジにする（**2026-08-11 オーナー確定**・4.6節）——手打ちの `p.42` も同じ見た目になる

なお、行頭の `>` を既に書いているユーザーは引用のつもりで書いているはずなので、そこが装飾されるのは**改善方向**の変化として扱う（7章のN0確認対象）。

## 1. 前提条件（確定・変更不可）

本書のすべての設計は以下の2条件を満たすこと。満たせない案は却下する。**2026-08-10 の方式転換後も両方とも維持される——変わるのは記法だけ。**

| # | 前提条件 | 意味するところ |
|---|---------|--------------|
| 1 | **つながりはメモ文字列内の記法であり、スキーマ変更ゼロ** | `UserBook.memo`（`String?`）・`MonthlyMemo.text`（`String`）は現状のまま。つながり用のSwiftDataモデル・プロパティ・リレーションを一切追加しない（**タグ欄のようなデータ項目も作らない**＝0.3節）。つながりはパース（表示時・インデックス生成時）で導出する |
| 2 | **R6（クラウド移行）と干渉しない** | 移行対象はプレーン文字列のままなので、移行ウィザード・Firestoreスキーマ（移行設計書 3.3節）・件数検証に変更は不要。`[[ ]]` を含むメモも含まないメモも、移行にとっては単なる文字列。R4.5がR6より先に出ても後に出ても成立する |

この2条件により、つながり機能は**ロールバック可能**（機能を消してもデータは無傷・`[[京都]]` という文字列がメモに残るだけ）であり、**リリース順序の自由度を奪わない**。

## 3. 記法設計（T1）

### 3.1 記法の選定（2026-08-10 改訂）

| 案 | 内容 | 判定 |
|----|------|------|
| A: `#タグ` | SNSで浸透・入力が軽い | **採用取り消し（2026-08-10）**。採用の決め手だった「入力の軽さ」は、日本語IMEでは全角 `＃` 対応や境界規則で補う必要があり実際には軽くなかった。ツールバー新設で入力問題自体が解けたため、優位性が消えた（0.3節） |
| **B': `[[中身]]`（共有ラベル）** | Obsidianで浸透した記法を「本と本をつなぐ線の理由」に使う。区切りが明示的なので**境界規則が不要**で、中身に任意の文字列を書ける | **採用（2026-08-10 オーナー確定）** |
| B: `[[タイトル]]`（直接リンク） | 本のタイトルを正確に書いて特定の本へ直接リンクする | **却下のまま**。タイトルを正確に入力する負担が大きく、表記ゆれで壊れる |
| C: `@メンション` | 「人」の含意が強く、本をつなげる用途に不自然 | 却下のまま |

> **重要な区別**: 初版が却下した案Bは「**タイトルを書いて特定の本へ直接リンクする**」案であり、却下理由（入力負担・表記ゆれで壊れる）はそちらに向いたものだった。今回採用した B' は**共有ラベル**——同じ中身を書いた本同士がつながる——であり、タイトルの正確さを要求しない。**一度却下した案を採用したのではない。**

### 3.2 パース仕様（2026-08-10 全面改訂）

```
開始   = "[["（"[" は半角 U+005B / 全角 U+FF3B のどちらでもよい・混在可）
終了   = 開始以降、最初に現れる "]]"（"]" は半角 U+005D / 全角 U+FF3D のどちらでもよい・混在可）
中身   = 開始と終了に挟まれた任意の文字列（空白・句読点・記号・絵文字可）
正規化 = 前後の空白をトリム → NFKC＋小文字化
無効   = 空・空白のみ・改行を含む・正規化後31文字以上（いずれも切り捨てず不成立）・未閉鎖（"]]" が無い）
入れ子 = なし。最初の "]]" で閉じる（"[[a [[b]]" は中身 "a [[b"）
```

- **区切りが明示的なので、`#` 時代の直前境界規則（行頭・空白・改行…）は丸ごと不要**。URLや `C#` の誤検出問題は構造的に存在しない。既存メモに `[[` が偶然含まれる可能性だけが残り、それは7章のN0確認で測る
- 抽出後の正規化はノードと同じ **NFKC＋小文字化**（`[[ＳＦ]]`＝`[[sf]]` を同一視）。**トリムを行う**のは中身に空白を許した帰結（`[[京都 ]]` と `[[京都]]` は同じつながり）
- **本棚内検索の正規化とは意図的に別物である（2026-08-07 オーナー確定・存続）**: 既存の `Utils/ShelfSearchMatcher.normalize` は `applyingTransform(.hiraganaToKatakana)` ＋ `folding(...)` ＋ 空白除去で、**ひらがなをカタカナへ寄せる**。NFKC はこれを行わないため、`[[とうきょう]]` と `[[トウキョウ]]` は**別のつながり**になる（本棚内検索では同一視される）。**検索は表記ゆれを吸収するのが目的、つながりはユーザーが書き分けたものを区別するのが目的**という役割の違いによる意図的な差であり、T2で `bookIndex.keywords` に載りノード側の自動抽出語と突き合わされるため（5.1節）、ノードの正規化と揃っている必要もある。**実用上の表記ゆれは「一覧で気づいて直す」で受ける**（2026-08-12 オーナー確定——当初は入力サジェストで発生自体を抑える計画だったが、サジェストは廃止した。4.1節）
- **改行を含む場合は不成立**（2026-08-10 オーナー確定）: 行をまたぐと表示（記号を隠した着色）も崩れる。閉じ忘れの `[[` が後続行の `]]` と誤って結合する事故もこれで防げる
- **手打ちも成立する正規の入力経路である**（2026-08-12 明文化）。パーサは入力経路を見ておらず、ツールバーの「つなぐ」も本文に `[[]]` という文字を挿すだけなので、**出来上がった文字列として手打ちと区別がつかない**。表示・編集画面のライブ装飾（記号隠しとまとまり削除）・サジェスト・集計インデックスはすべてこの1つのパーサを通る（3.3節）ため、経路によって成否が変わることは構造的に起きない。ただし入力の**主経路はツールバー**（4.5節）であり、記号を打てることを前提にした設計にはしない
- **全角を受けるのは `[[ ]]` だけ——太字 `**`・引用 `> `・ページ番号 `p.` は半角限定のまま揃えない（2026-08-12 オーナー確定）**。前提9は `[[ ]]` に固有の判断であり、根拠は**日本語IMEで全角になるのは記号だけで、英字は全角にならない**という非対称にある:
  - **`[[ ]]` は受ける**——かな入力のまま打つと**必ず** `［［` になる。かつObsidian経験者が手で打つ実需があるので、全角を受ける価値がある
  - **`**` と `> ` は受けない**——かな入力では `＊` `＞` が出るが、**これらを手打ちするのはMarkdown経験者であり半角を使う**。受けると誤検出が増えるだけで、`＊＊＊` の区切り線・`A＞B` の比較記号・`＞＞` で始まる表記が意図せず装飾になる
  - **`p.` は対応が不要**——かな入力では `p` そのものが打てず、英数へ切り替えれば半角になる。**全角になりようがない**
- パーサは**純関数**（`String → [MemoLink]`、表示位置レンジ＋正規化キー）としてユニットテスト対象にする（実装ガイド 5章）

### 3.3 なぜスキーマ変更ゼロで成立するか

つながりは「メモの中に既にある文字列」であり、データとして二重管理しない:

- **表示時**: メモ文字列をパースして記号を隠し中身を着色（`AttributedString`）
- **集計時**（絞り込み＝ステップ8'）: 全書籍のメモをパースして「つながり→本」のインデックスをメモリ上に構築（425冊規模なら数ms・キャッシュはメモリのみ）
- **T2**: ノードのインデックス生成パイプラインが元々メモ本文を読んでいる（ノード設計書 3章）ので、その中で `[[ ]]` も抽出する — 保存先は既存計画の `bookIndex.keywords` であり、SwiftData/Firestoreのユーザーデータスキーマには触れない

**表記ゆれをどこで受けるか（2026-08-12 オーナー確定・サジェスト廃止に伴う整理）**

サジェストは「表記ゆれの発生自体を抑える」ための仕組みだったが、**気づいて直す**方式へ切り替えた。担い手は次の2段階になる:

1. **気づく場所は絞り込みUI（ステップ8'・R4.5）**——本棚の絞り込みに出るつながりチップの一覧に、`[[京都]]` と `[[きょうと]]` が**別々に並ぶ**。パーサはかな寄せをしない（前提4）ので機械的に同一視されることはなく、一覧がそのままゆれの可視化になる。**R5を待たずここが先に効く**のが重要——T1の範囲内で「気づく」までは成立する
2. **直す手段はノードビュー（R5）の要件**——気づいたあと、そのラベルを使っている本を1冊ずつ開いてメモを書き換えるのでは実用にならない。したがって **R5のノードビューには「つながりのラベル一覧」に加えて、そこからラベルを*リネーム*・*統合*できる手段を入れる**（複数のラベルを1つへまとめる操作を含む）。実装はメモ本文の一括置換になる（つながりはスキーマを持たないため・3.3節）。**ノード設計書へ申し送り済み**

この2段階が揃うまでは「気づけるが、直すのは手作業」という状態が残る。T1のスコープでは許容する（つながりを1つも使わないユーザーには影響がなく、使い始めた直後のゆれは本数が少ないうちに直せる）。なお **T1でラベルの編集UIを作らない判断（4.2節）は変えない**——直す手段はノードビュー側に置く。

### 4.2 T1でやらないこと

- つながりの編集・リネーム・削除の専用UI（メモ本文を編集すれば変わる。それがスキーマレスの利点）。**ただしリネーム・統合はR5ノードビューの要件として立てた**（2026-08-12 オーナー確定・4.1節）——T1で作らないという判断は変えず、行き先を決めたということ
- **入力サジェスト**（2026-08-12 廃止・4.1節）
- つながり一覧画面・クラウド表示（絞り込み導線で十分。利用状況を見て判断）
- **太字 `**`・行頭 `>` 以外のMarkdown解釈**（見出し・箇条書き・斜体・リンク等。0.4節の「ボタンで入れたものだけが装飾になる」約束）
- **文字色・フォント変更**（0.4節の3理由）
- メモ内の `[[ ]]` を直接タップする導線（4.4節・案a）
- ノードグラフとの連携（T2 = R5）
- **月メモ（`MonthlyMemo.text`）のつながり**（4.3節）

### 4.3 月メモをT1のスコープから外す理由（2026-08-07 オーナー確定・存続）

初版ドラフトは対象を `UserBook.memo` と `MonthlyMemo.text` の双方 (仮) としていたが、**T1では書籍メモのみを対象とし、月メモは T2以降の検討項目へ送る**（8章）。理由は2つ。

1. **表示箇所が存在しない**: 月メモの本文は、編集中の `MemoEditorView` の `TextEditor` の中以外、**カレンダーを含めどの画面にも表示されていない**（`BookshelfCalendarView` にあるのは編集ボタンのみ）。パースしても装飾を出す場所が無く、T1の機能のうち「表示」が成立しない
2. **インデックスの形が変わる**: 書籍メモのつながりは「ラベル → 本」で直接結びつくが、月メモでは「ラベル → 月 → その月に読んだ本すべて」という間接的な結びつきになる。3.3節のインデックスとは別の構造を要し、絞り込みの意味論も別途決める必要がある

月メモを扱うなら、この意味論を決めたうえで T2 のエッジ設計（「メモ同月」軸が既に 5.2節にある）と併せて考えるのが筋である。

### 4.4 タップ導線は「詳細画面のつながりチップ行」（2026-08-07 オーナー確定・存続）

**書籍詳細につながりチップの行を足し、操作はそのチップが持つ**。メモ本文の着色は「これはつながりである」という**表示**のまま残し、**操作はチップが持つ**という役割分担。同じラベルが本文とチップに二重に出るが、意味が違うので冗長にはならない。実装はT1の絞り込み（4.1節）とまとめて行う。

**この形を採る理由**:

1. **タップ先が衝突しない**。`UserBookDetailView` のメモ欄は全体が「タップでメモエディタを開くボタン」であり、メモの一部だけ挙動が変わると**誤タップしたとき何が起きたか分かりにくく、戻る操作も直感的でない**
2. **本棚の絞り込みUIでチップ方式を選んだ判断と揃う**（4.1節）。同じ「つながりを操作する要素」が画面ごとに別の形をしているより、一貫しているほうが説明が要らない
3. **つながりが1つも無い本では行ごと出ない**ので、使わない人の詳細画面は現状のまま維持される

### 4.5 ツールバー（2026-08-10 オーナー確定・新設）

メモ編集欄（`MemoEditorView`）の下に置く。**つなぐ｜太字・引用・ページ番号｜書式クリア・ひとつ戻す**の3組を区切り線で分け、各ボタンは**アイコン＋ラベル**（**2026-08-11 オーナー指示**・アイコンは `Assets.xcassets` の imageset）。左から:

| ボタン | 動作 |
|--------|------|
| **つなぐ** | **トグル**（**2026-08-12 オーナー指示**——後述）。中にいなければ `[[]]` を挿入しキャレットを括弧の中へ。**記号は画面に出さない**（**2026-08-12 オーナー指示**・4.6節）ので、押したあとに見えるのは案内（「つながりを入力」）だけ。括弧から出るのは、外を触るか**Enterで括弧の外へ出る**とき。**サジェストは出さない**（同日確定・4.1節で廃止）。**ツールバーは畳まない**（**同日 実機確認で差し戻し**——いったん「書いている間は畳む」としたが、消えるより*どの装飾の中にいるか*が分かるほうが要る。下記のアクティブ表示に置き換えた） |
| **太字** | **トグル**。中にいなければ選択範囲を `**` で囲む（無選択なら `****` を挿入しキャレットを中へ） |
| **引用** | **トグル**。付ける側は、無選択ならキャレット行の行頭に `> ` を挿入。**行の一部を選んだ場合はその部分を独立した行に切り出して引用にする**（改行を入れて行を分ける・**2026-08-11 オーナー指示**——引用は行単位の仕組みなので、そのままでは選んでいない前後の文字まで囲みに入る）。複数行の選択は各行に付ける＝ひとつの囲みにまとまる。あわせて**引用の直後に出典ページの行（`p.`）を自動で用意する**（**2026-08-11 オーナー確定**・4.6節）——入力は任意で、空のままなら保存時に消える |
| **書式クリア** | **メモ全体**から装飾を外す（**2026-08-11 オーナー確定**）。`**`・`[[ ]]`・行頭の `> ` に加え、**ページ番号は数字ごと落とす**（同日指示——数字を残すとバッジのままで「装飾が消えない」ため。ページ番号だけの行は空行を残さないよう行ごと、文中のものはその部分だけ）。取り消せる操作なので、意図せず消しても「ひとつ戻す」で戻せる。ペアになっていない `**` や閉じていない `[[` は本文の文字なので触らない。組み立ては純粋関数 `MemoPlainText` |
| **ひとつ戻す** | 直前の操作を取り消す。**iOS標準の取り消し機構に相乗りする**（**2026-08-11 オーナー確定**）——文字入力もツールバー操作も同じ履歴に載るので、ボタンの名前と挙動が一致する。このためツールバーの書き換えは**テキストビュー経由**（`MemoEditorBridge`）で行う。文字列を直接差し替えると履歴に残らない。戻せる操作が無いときは薄くして押せなくする。取り消すと**復元された範囲が選択される**ので（書式クリアを戻すと全選択に見えた・同日修正）キャレットに畳む |
| **ページ番号** | `p.` を挿入しキャレットを直後へ（数字はユーザーが打つ）。**文字を挿入するだけの入力補助**であり、ページへのリンクではない（表示側でバッジにするのは4.6節）。あわせて**キーボードをテンキー（`.numberPad`）へ切り替える**（**2026-08-11 オーナー指示**・当初の `.numbersAndPunctuation` から差し替え。ページ番号は数字しか打たないので、記号や文字が並んでいると打ちにくい）。テンキーには文字入力へ戻る鍵が無いが、キャレットが `p.数字` から離れれば通常のキーボードへ自動で戻るので、他の行に触るか `p.` を消せば抜けられる |

- 書式は**Markdown記法を本文に埋め込む方式**。ボタンは記号を挿入するだけで、独自のリッチテキスト形式を持たない（前提1・エクスポート互換・ロールバック可能性のすべてに効く）
- **つなぐ・太字・引用は押すたびに付いたり外れたりする（トグル）**（**2026-08-12 オーナー指示・新設**——「つなぐ」を連打すると `[[[[]]]]` と入れ子になり、外側だけが装飾として成立して `]]` が画面に露出していた。実機で発覚）。**いまその装飾の中にいれば外す**——つながりと太字は記号だけを外して中身を残し（中身が空の `[[]]` は跡形なく消える）、引用は行頭の `> ` を外す。判定はアクティブ表示（上記）と同じ `MemoActiveFormats` の規則なので、**光っているボタンをもう一度押せば消える**という読み方で一致する。組み立ては純粋関数 `MemoFormatToggle`（画面の中に書くとテストで固定できない・`MemoQuoteInsertion` と同じ理由）
    - 引用を外すときは**直後の空の出典ページの行も一緒に落とす**——引用でなくなると `p.` は置き場を失い、本文に文字として残ってしまう。**数字が入っている行は残す**（ユーザーが打ったものを消さない。行頭のバッジとして表示される）
    - 複数行にまたがる選択で引用を外すのは、**触れている行がすべて引用のとき**だけ。一部でも普通の行が混ざっていれば付ける側の操作と見なす
    - **ページ番号はトグルにしない**——`p.` の中にいるあいだはテンキーでツールバーが畳まれており、押しようがない
- **選択範囲からは隠れている記号を外してから囲む**（**2026-08-12 オーナー報告**——引用の中で行頭から文字を選んで「つなぐ」を押すと、見えていない `> ` まで囲まれて `[[> 引用]]` になり、引用が解除されていた）。記号は消さずに極小フォント＋透明で隠しているだけなので（4.6節）、行頭から選ぶと選択に入ってしまう。両端をそれぞれ内側へ寄せる（`MemoHiddenMarkers.trimming`）。行頭・行末のどちらでも起こるので両側を見る
- ボタンは**アイコン＋ラベル**（6語・5言語ローカライズ）で出す（**2026-08-11 オーナー指示**・当初の「テキストラベルのみ」から差し替え。図像だけでは操作の意味が伝わらないためラベルは残す）。リンクに汎用の図像（https:// を思わせるもの）は使わない。アイコンは**すべて18×18の同じ画布で書き出し、表示も同じ大きさ（20）で揃える**（2026-08-11 オーナー指示）——当初は書き出しの画布がまちまち（10×14〜22×21）だったため表示側で2段階に振り分けていたが、画布が揃った以上、コード側で大きさを振り分けるとかえってばらつく。図像の中の余白は素材側で調整する。**横スクロールはしない**（2026-08-11 オーナー指示）——スクロールに逃がすと端のボタンが隠れて気づけない。ボタンの幅は**ラベルに合わせ、余りを均等な間隔に配る**（同日指示。幅を等分すると、ラベルが短いボタン（太字・引用）の周りだけ隙間が広く見える）。ラベルの文字は10（`.caption2` の11から1段小さくした・同日指示）。見た目は**キーボードから浮いたカプセル**（**2026-08-11 オーナー指示**）——左右を丸め、下に6の隙間、左右も8だけ内側に置く。本文と同じ白の上では材質だけだと境目が消えるので、細い輪郭（`separator` 0.5）と淡い影を添える。カプセルの丸みが端のボタンを削らないよう内側の余白は16に広げ、区切り線は縁に触らない高さ（32）にする。**出典ページの入力中（テンキー）はツールバーを畳む**（**2026-08-11 オーナー指示**）——背の低いテンキーへ替わる一瞬、ツールバーが元のキーボードの高さのまま浮いて見える（スクロールすると直るが、その一瞬を見せたくない）。数字の入力に使えるボタンも無いので、出しておく理由がない。専用の行に差し替える案は採らない（2026-08-11 オーナー確定）。テンキーには改行キーも文字へ戻る鍵も無いため一度は「ページ番号を入力／完了」の専用行を用意したが、行き先の空行（4.6節）を用意した時点で**余白を触るだけで抜けられる**ようになり、役目を失ったため取り下げた（7つ目のボタンとして並べる余地も無い——6つで画面幅をほぼ使い切っている）。長い訳語（例: Clear format）はラベルを縮めて収める
- ツールバーは**キーボードの上の領域を単独で使う**（**2026-08-12 整理**——サジェスト行を廃止したので、ここに重ねて出るものは無くなった）。編集中は常に出し、**畳むのは出典ページの入力中（テンキー）だけ**（**2026-08-12 オーナー確定**——つながりを書いている間も畳まない）
- **キャレットが入っている装飾のボタンは光らせる**（**2026-08-12 オーナー指示・新設**）。太字の中なら「太字」、引用の行なら「引用」、つながりの中なら「つなぐ」、`p.数字` の中なら「ページ番号」を**テーマ色**にする（本文の装飾と同じ色なので、ボタンと本文のどちらを見ても同じ意味に読める）。これは畳む仕様の**代わり**に入れたもの——記号を隠した以上、いまどの装飾の中にいるかは画面から読み取れず、それを伝える役をツールバーが引き受ける。装飾は重なりうるので**同時に複数光ってよい**（引用の中のつながり）。範囲を選んでいるあいだは光らせない（選択の中に装飾の内と外が混ざりうるため）。判定は純粋関数 `MemoActiveFormats`（「そこで文字を打ったらその装飾になるか」で揃える。記号の上も装飾の中と見なす）
- 月メモの編集でも**ツールバーは出す**（太字・引用・ページ番号はメモ一般の書式であり、月メモを除外する理由がない）。ただし「つなぐ」ボタンは書籍メモのみ（4.3節のスコープ。`MemoEditorView(allowsLinks:)` で出し分ける）

### 4.6 表示仕様（書籍詳細のレンダリング・2026-08-10 オーナー確定）

`UserBookDetailView` のメモ欄で解釈するのは次の4つ**だけ**（**記号の全角を受けるのは `[[ ]]` のみ。他の3つは半角限定**——理由は3.2節）:

| 記法 | 表示 |
|------|------|
| `[[中身]]` | 記号を隠し、中身だけテーマ色＋セミボールドで着色 |
| `**中身**` | 太字（ペアが成立している場合のみ。`*` 1つの斜体は解釈しない）。太さは標準の太字より一段上の `heavy`（**2026-08-12 オーナー確定**——`bold` では本文との差が弱い）。この太さは「太く」の指定では出せないので、**行の大きさに合ったフォントを当てる**（引用の中は本文より小さいため、呼び出し側から渡す） |
| 行頭の `> ` | 引用の装飾。記号を隠し、**薄いグレー背景で囲む**。囲みの中の文字は**本文より少し薄い黒**（`label` の75%・2026-08-11 オーナー指示。編集画面と共有する）（角丸なし＝編集画面と揃える・**2026-08-11 オーナー確定**——当初の縦線 `│ ` 置換は「記号が引用と伝わらない」ため差し替え。記号ではなくUIで表現する）。連続する引用行はひとつの囲みにまとめる。実装はメモ表示を1つの `Text` からブロック分割（`MemoTextBlocks`）へ変更した。`>` 単独や空白なしの `>text` は解釈しない＝ボタンが挿入する `> ` の形だけ |

  - **編集中はページ行を常に用意しておく**（**2026-08-11 オーナー指示**）——一度消すと案内が出ず、そのメモにはもうページを入力できなくなる。そこで(1)編集画面を開くとき（`MemoEditorView.init`）と(2)入力のたび（`textViewDidChange`）に、ページ行の無い引用へ `p.` の行を足し直す（`MemoQuotePage.pageLineInsertions` / `ensuringPageLines`）。**この行より前に入った分だけキャレットを送る**（引用の行末に入るので、同じ位置なら動かさない）。取り消しの履歴には載せない——自動で足したものを戻す操作は意味を持たない。あわせて**数字が未入力の `p.` は消せない**（`MemoQuotePage.protectsDeletion(of:in:)`）——通しても足し直すため、`p` だけが残る／`p.` が引用の行に流れ込むといった壊れ方をする。直前の改行も同じ理由で守る。数字はふつうに消せて、消し切れば案内に戻る。この自動挿入で「変更あり」にならないよう、`hasChanges` は**保存する形**（空のページ行を落とした結果）と比べる
  - **キャレットがこの行に入ったら `p.` を出し、案内は下げる**（**2026-08-11 オーナー指示**——数字を打つ位置が分かるように。出す `p.` も装飾なし）。あわせて**キャレットは `p.` の直後より前に置かない**（`MemoQuotePage.caretLocation(snapping:in:)`）。案内中の行は文字が幅ゼロでどこを触っても行頭に入りうるため、押し戻さないと「21p.」の順に入り、ページの行としても成立しなくなる（右下寄せもバッジも外れる）——実機で発覚
  - ツールバーが加える差分（行の切り出し・ページ行の用意・キャレット位置）は**純粋関数 `MemoQuoteInsertion` に集約**する。経路ごとに書いていた実装で無選択の経路がページ行を足し忘れ、実機まで気づけなかったため（同日）。画面の中に閉じているとテストで固定できない

## 5. ノードグラフ連携（T2・R5ノードβに同梱）

### 5.1 統合点

ノード設計書のパイプライン（正規化→言語判定→抽出→ストップワード→IDF）に対し、つながりは**別レーンで合流**する:

```
メモ本文 ─┬─ 自動抽出レーン: NLTagger/フォールバック → ストップワード → IDF → keywords (source: "memo")
          └─ つながりレーン: [[ ]] パース（3.2節）→ そのまま採用      → keywords (source: "link")
```

- つながりレーンには**ストップワードもIDF減衰も適用しない**。ユーザーが意図して書いたラベルを機械が却下しない（前提7）
- `bookIndex.keywords` の要素に `source: "link" | "memo" | "title"` を持たせる（**旧記述の `"tag"` から改名・2026-08-10**。R5は最初からFirestore保存＝N2統合のため、ローカルキャッシュの移行は発生しない。schemaVersionの初版に含める）

### 5.2 エッジ重み（順序のみ確定・2026-07-19・存続）

**確定しているのは順序関係のみ**: シリーズ 1.0 > **つながり共有** > 著者 0.6。**具体値はノードβの実データで調整する**。

| 軸 | 重み | 備考 |
|----|------|------|
| シリーズ | 1.0 | 既存（ノード設計書 5章） |
| **つながり共有** | **1.0と0.6の間（具体値はノードβで調整）** | **新設**。「ユーザーの宣言」はシリーズ判定に次ぐ確実さ。reasons表示はラベルそのもの（例:「京都」。記号は付けない） |
| 著者 | 0.6 | 既存 |
| 共有キーワード | 0.15×IDF（3個上限） | 既存・自動抽出 |
| メモ同月 | 0.05 | 既存 |

- つながり共有はエッジ上限（k=8）・スコア下限の枠組みには従う（手動だけ特別扱いして毛玉化したら本末転倒）
- 同一ラベルを大量の本に付けた場合（例: 30冊に `[[積読]]`）は完全グラフ化して毛玉になるため、**1ラベルあたりのエッジ生成上限（共有本数が15冊を超えるラベルはエッジ生成から除外し、絞り込み機能でのみ有効）**を設ける — 自動抽出のIDF足切りと同じ思想の安全弁
- 重みの具体値の調整には N0ハーネスを再利用できる（つながり軸を足して再走）

### 5.3 R5への要件: ラベル一覧とリネーム・統合（2026-08-12 オーナー確定・新設）

**ノードビュー（R5）に「つながりのラベル一覧」と、そこから*リネーム*・*統合*できる手段を入れる**。T1で入力サジェストを廃止し、表記ゆれを「気づいて直す」方式に切り替えた（4.1節）ことの後半＝**直す手段**がこれにあたる。

- **なぜノードビューか**: ラベルはエッジの理由であり、一覧して整えたくなる場所はグラフの側にある。T1の絞り込みチップは「気づく」までを担うが（4.1節）、絞り込みUIに編集機能を持たせるのは役割が混ざる
- **なぜ必須か**: 気づいても、そのラベルを使っている本を1冊ずつ開いてメモを書き換えるのでは実用にならない。**一覧だけを出して直す手段を用意しないと、気づかせた分だけ不満が増える**
- **実装の形**: つながりはスキーマを持たないので（3.3節）、リネームも統合も**該当する本のメモ本文の一括置換**になる。置換対象は `MemoLinkParser` が返すレンジそのもの（`[[ ]]` を含む範囲）なので、本文の他の文字には触らない。統合は「複数のラベルを1つの綴りへ寄せる」＝同じ置換を複数キーに対して行う操作
- **注意点として先に挙げておくもの**: ①置換は複数冊のメモを書き換えるため、取り消し（または確認の一段）が要る ②R6のクラウド同期後は書き換えが同期対象になる ③正規化キーが同じで綴りだけ違うもの（`SF`/`sf`）は既に同一のつながりなので、統合の対象は**キーが異なるラベル**に限る
- **ノード設計書へ申し送り済み**（先方の要件一覧に追記）

### 5.4 自動抽出との関係

つながりが普及すれば「メモ由来の自動抽出語」の役割は縮小しうるが、**当面は併存**（前提8）。`[[ ]]` を1つも書かないユーザーにも自動のつながりは価値があるため。ノードβでの実測（利用率・雑音エッジ報告）を見て、メモ自動抽出語の重み引き下げ・廃止を判断する。**ノード設計書 0.2節の方針1（自動生成・手動タグ付け不要）とは併存する**——方針1は「本を登録するだけでグラフが成立する」ベースラインの話として維持され、`[[ ]]` はその上に任意で足す手動エッジである（先方0.2節に追記済み）。

## 9. `#` 記法時代の記録（2026-07-19〜2026-08-10）

方式転換前に `#タグ` 記法で実装・確定した内容の記録。コミット履歴（`702a657` パーサ / `dcaea11` 連続タグ緩和 / `95c905b` ハイライト / `cee06e3` サジェスト）と突合するためのもの。**`#` は未リリースのため、ユーザーデータへの影響はない。**

**破棄（`#` 固有で、`[[ ]]` では不要になったもの）**:

- 直前境界規則（行頭・空白・改行・タグ直後）と、その緩和（連続タグ）。区切りが明示的な `[[ ]]` では境界問題が構造的に存在しない
